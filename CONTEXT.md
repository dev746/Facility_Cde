# CONTEXT.md — Facility CDE v2 Reference Manual

This document provides a complete overview of the Facility Common Data Environment (CDE) v2 codebase. It serves as a technical context guide for any LLM or developer working on the system.

---

## 1. System Overview
Facility CDE v2 is a cross-functional data integration engine designed to aggregate and query industrial manufacturing data. It receives unstructured and semi-structured data from multiple sources (such as computer vision tracks, batch scrap measurements, and worker telemetry/field reports) and exposes it via a unified API and a WhatsApp interface.

The system is built on **PostgreSQL** using a multi-schema architecture to keep domain data isolated, while presenting a unified view to users.

## 2. Multi-Schema Database Architecture

The database is divided into the following isolated PostgreSQL schemas:

### A. `core` Schema
Stores canonical reference data for assets and shared cross-functional entities.
*   **`core.assets`**: Central asset registry containing unique `asset_id`, `name`, `type`, `location`, `line`, `zone`, and `status`.
*   **`core.expert_notes`**: Annotations left on assets by human engineers.
*   **`core.findings_unified`**: A database view consolidating computer vision detections, scrap batches, and manual reports into a single queryable model.

### B. `cv` Schema
Stores telemetry and outputs generated by computer vision submodules.
*   **`cv.detections`**: Instantaneous anomaly/wear detections with `confidence` scores.
*   **`cv.tracks`**: Real-time object tracking logs.

### C. `scrap` Schema
Stores structural metrics from scrap sorting or piece inspection.
*   **`scrap.batches`**: High-level batch information containing material scaling ratios (`cm_per_pixel`).
*   **`scrap.scraps`**: Geometrical profiles of individual scrap items.

### D. `auth` Schema
Houses permissions, roles, and user state.
*   **`auth.users`**: Registered operators containing `phone`, `name`, `role`, and `is_active`.
*   **Permissions Matrix**: Roles map directly to permitted conversational intents (`admin`, `expert`, `technician`, `viewer`).

## 3. Data Ingestion Pipeline

### Watched Folder Ingest
The background watch module (`ingestion/watcher.py`) polls `data/inbox/`. When a new file is detected:
1.  **Format Detection** (`ingestion/detector.py`): Determines format type based on keys (`batch`, `cv`, `annotations`).
2.  **Normalization** (`ingestion/normalisers.py`): Converts raw payloads into canonical `make_asset` and `make_finding` models.
3.  **Universal Router** (`ingestion/universal.py`):
    *   Inserts or updates assets in `core.assets`.
    *   Routes domain data to target tables (e.g. CV anomalies to `cv.detections`).
4.  **Logging**: Execution outcomes are logged directly to `ingest.files`.

---

## 4. Query & Command Interface

User queries are resolved using a two-stage pipeline:
1.  **Intent Parsing** (`query/intent.py`): Classifies user inputs into structured commands (e.g. `machine`, `findings`, `telemetry`, `summary`, `critical`).
2.  **Resolution & Formatting** (`whatsapp/commands.py`): Resolves references, queries database schemas, and constructs formatted markdown strings.

*All database operations are fully qualified (e.g. querying `core.assets` instead of `assets`) and use parameterization (`%s`) for stability.*
